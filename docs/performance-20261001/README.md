# 초기 화면 표시 개선 · 2026-10-01

이미지 용량을 줄인 뒤에도 첫 화면 이미지 요청과 화면 생성이 JavaScript 초기화 뒤로 밀리고 있었다. 리소스를 더 압축하는 것만으로는 부족해, 공개 페이지를 빌드할 때 HTML로 만들고 브라우저에서는 기존 화면에 React 기능을 연결하도록 바꿨다. 원본 작품 이미지·영상과 기존 압축 품질, 레이아웃과 콘텐츠를 유지했다.

## 적용 범위

- 공개 화면 74개를 `dist/pages/`에 정적 HTML로 생성한다. React의 비동기 페이지 모듈을 먼저 준비한 뒤 렌더링해 미완성 Suspense 출력이 들어가면 빌드가 실패한다.
- CloudFront는 빌드된 2026년 경로 목록에 있는 URL만 정적 HTML로 연결한다. 관리자, 스토어 별칭, 잘못된 경로와 2024·2025년은 기존 SPA 및 리다이렉트 처리를 유지한다.
- 페이지 코드를 분리하고 필요한 모듈·첫 화면 이미지·폰트를 미리 요청한다. CSS는 초기 HTML에 포함해 별도 스타일 요청을 기다리지 않는다.
- 한글은 첫 진입 페이지에 쓰이는 글자만 작은 파일로 제공하고 기존 전체 문자용 폰트를 보완용으로 유지한다. 다른 페이지로 이동하거나 새로운 글자가 추가되어도 표시할 수 있다.
- Open Sans의 사용하지 않는 너비 축을 기본값으로 고정하고 기본 문자와 확장 문자를 나눴다. 기존 굵기와 라틴 443자 지원은 유지했다.
- 홈 영상은 HTML의 반응형 `source`로 같은 모바일·데스크톱 파일을 선택한다. 자동재생, 이전·다음 전환, 모바일 컨트롤은 유지했다.

요소 비교에서는 외부 YouTube 화면을 양쪽에 동일하게 고정했다. 별도 실제 기능 검사에서는 사이트 자체 JavaScript·HTTP 오류가 없었다. 외부 YouTube 스크립트에서 간헐적인 `compute-pressure` 권한 정책 콘솔 메시지를 관찰했으며, 이를 사이트 자체 오류와 구분했다.

`layout-summary.json`, `interaction-summary.json`, `font-validation.json`, `cloudfront-routing-validation.json`, `cloudfront-development-tests.json`에 검증 요약을 남겼다. `release-identity.json`은 검증 빌드의 파일 해시다. Lighthouse 점수는 네트워크와 실행 조건에 따라 달라지므로 로컬 실험 점수를 운영 사이트 측정치와 섞어서 해석하지 않는다.

## 배포와 복구

배포는 해시 리소스 업로드 → HTML 업로드 → CloudFront 개발 단계 테스트 → 함수 게시 → 캐시 무효화 순서로 진행한다. HTML은 캐시하지 않고, 해시 리소스는 장기 캐시한다. 이전 해시 파일을 즉시 삭제하지 않아 배포 중 기존 탭의 요청이 깨지지 않도록 했다. 배포 작업은 동시에 실행되지 않는다.

함수 수정 전에는 배포 대상 도메인·연결 함수·현재 버전을 확인한다. 다른 미게시 변경이 있으면 덮어쓰지 않고 중단한다. 기존 함수와 수정본은 Actions의 `cloudfront-routing-backup` 아티팩트로 보관한다. 정적 경로 연결을 되돌릴 때는 백업 함수 코드를 새 개발 버전으로 적용·테스트·게시하면 된다. `index.html`은 빈 루트의 SPA 진입점으로 계속 남으므로 기존 경로 처리로 복구할 수 있다.

## 콘텐츠를 수정할 때

`npm run build`가 최신 팀·멤버 데이터에서 정적 페이지와 경로 목록을 다시 만든다. 새 경로에 전용 폰트가 없어도 기존 폰트로 표시되지만, 필요한 글자만 먼저 받도록 아래 생성 작업을 함께 실행할 수 있다. 생성된 폰트와 메타데이터는 커밋하며 CI에서 Python은 필요하지 않다.

```sh
# fonttools[woff] 환경에서 실행
python scripts/generate-fonts.py
python scripts/generate-route-fonts.py
npm run build
```

`VITE_STORE_ONLY_MODE=true` 빌드는 정적 공개 페이지를 생성하지 않고 기존 스토어 전용 SPA 처리를 사용한다.

## 첫 화면 아래 영상과 중간 크기 이미지

운영 재측정에서 RE:I의 첫 화면 밖 YouTube가 초기 로딩에 포함되는 것을 확인했다. 기존 `loading="lazy"`를 유지하되 `IntersectionObserver`로 영상 프레임이 보일 때 주소를 연결하도록 했다. 모바일·데스크톱 14건에서 화면 밖·숨김 분기는 요청하지 않고, 스크롤 후 동일한 영상 주소를 사용하며 프레임 크기가 유지되는지 확인했다.

모바일에서 768px 포스터를 선택하던 구간에는 640px 파생본을, 프로필에는 320px 파생본을 추가했다. 기존 크기도 그대로 유지한다. 원본과 압축 설정은 같으며 브라우저가 화면 크기와 픽셀 밀도에 맞춰 선택한다. 전시 정보 포스터 파일은 64,494B → 49,128B(23.8%), RE:I는 148,522B → 95,880B(35.4%)로 줄어든다. 새 크기는 포스터와 프로필에 한정해 전체 이미지 목록이 불필요하게 커지지 않도록 했다.

폰트 파일을 HTML에 직접 포함하는 방법도 로컬에서 비교했지만 점수 개선이 없어 채택하지 않았다.

## 비하인드의 초기 플레이어 요청 순서

전체 운영 측정 후 비하인드에서 초기 외부 플레이어 요청과 글 표시가 겹치는 문제를 추가 확인했다. 팀 화면에서 검증한 `LazyIframe`을 비하인드에도 재사용해 초기 HTML의 글과 레이아웃이 먼저 표시되고, React 연결 후 화면 안에 있는 동일 YouTube 플레이어가 로딩되도록 했다. 영상의 주소·크기·컨트롤과 갤러리 기능은 유지했다.

동일 로컬 gzip HTTP/1.1 환경에서 변경 전후 각각 3회 측정했다. 성능 점수는 89·87·91 → 96·95·96(중앙값 89 → 96), FCP 중앙값은 2.53 → 1.81초, LCP 중앙값은 2.92 → 2.56초였다. 런웨이에도 같은 방법을 시험했지만 점수 개선이 없어 변경을 제외했다. 이 수치는 운영 측정과 별도다.

비하인드는 375·412·768·1024·1440·1920px에서 디자인 비교 6건을 추가 통과했다. 모바일·데스크톱 실제 영상 재생과 갤러리 마지막→처음·이전 복구·Escape·스크롤 복구도 확인했다. 근거는 `behind-performance-comparison.json`, `behind-layout-comparison.json`, `behind-interactions.json`, `behind-release-identity.json`에 남겼다.
